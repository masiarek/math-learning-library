# Machine numbers

**Level:** 201 → 301 · for anyone who has used a float

**One line:** A float is not a blurry real number but an exact member of a finite set picked by four numbers — radix, precision and two exponent limits — and every operation is exact arithmetic followed by a rounding function, which decides, law by law, what survives of real arithmetic.

## A finite set standing in for the real line

The first three lessons of this chapter were about numbers that came from a measurement, whose later digits were never known. This one is about a different gap: the one between mathematics and the machine.

A computer can hold only finitely many different numbers, and the real line has uncountably many points. So almost all of them are missing, and not by bad luck. A finite set has [measure zero](../../02_Measure_Zero/what_measure_zero_means/README.md), so a real number picked at random is a machine number with [probability zero](../../02_Measure_Zero/probability_zero/README.md).

What is striking is how little it takes to describe the set the machine keeps instead. Four numbers do it:

| symbol | name | binary64, Python's `float` |
|---|---|---|
| β | radix | 2 |
| p | precision, in digits | 53 |
| e_min | smallest exponent | −1022 |
| e_max | largest exponent | 1023 |

A normal member is ±d₀.d₁d₂…d₍ₚ₋₁₎ × β^e, with d₀ ≠ 0 and e between e_min and e_max: scientific notation with exactly p significant digits and a limited exponent. That is the whole definition.

Every member is an exact number. The toy member `0.625` below is precisely five eighths. The approximation is not inside the members; it is in the step that forces a real result back into the set.

The *Handbook of Floating-Point Arithmetic* opens by making the same point: a finite set cannot keep every property of real arithmetic, so every format trades speed, accuracy, range, simplicity and memory against each other. This page takes that literally. Section 4 finds out which properties are kept, and section 7 what each of the four numbers buys.

The program builds a system small enough to print whole — β = 2, p = 3, e from −1 to 2 — tests the laws of arithmetic against every one of its members, and then shows that Python's `float` is the same construction with bigger numbers.

## The gaps are a ruler whose marks spread out

Section 2's ruler is the picture to keep. Between one power of 2 and the next, the members are evenly spaced, and at each power of 2 the spacing doubles. The absolute gap grows with the numbers while the relative gap stays inside a fixed band: 1/7 to 1/4 in the toy system, about 1.1 × 10⁻¹⁶ to 2.2 × 10⁻¹⁶ in binary64.

That is exactly what [significant figures](../significant_figures/README.md) are. A float stores a fixed number of significant digits, like `:.17g`, and never a fixed number of decimal places, like `:.2f`. Between 2⁵³ and 2⁵⁴ the gap is 2, so no odd integer there is a member, which is why `2.0**53 + 1.0 == 2.0**53`.

**The hole at zero** is the one place the ruler has to be patched. With only normal members, nothing lies between 0 and the smallest normal number, so two different members can differ by less than that: `0.625 − 0.5` rounds to 0 although the two are not equal. IEEE 754 fills the hole with **subnormals** — significands with a leading zero, allowed only at the lowest exponent. They give up significant digits to keep the spacing even all the way down to zero, and section 4 shows what that buys: two laws that hold with subnormals and fail without them.

## Rounding is a function

The *Handbook*'s second chapter frames rounding the way it is best understood. A **rounding function** ∘ sends every real number to a member, or to an infinity, and a floating-point operation is *defined* as a ⊕ b = ∘(a + b). The exact sum is taken first, as a real number, and only then rounded. IEEE 754 requires this **correct rounding** for +, −, ×, ÷ and √, which is why every float result on this page is the same on every machine that follows the standard.

There are five rounding functions, and section 3 prints all of them side by side:

- **RD**, toward −∞: the largest member ≤ x.
- **RU**, toward +∞: the smallest member ≥ x.
- **RZ**, toward zero: RD for positive x, RU for negative x.
- **RN even**, to nearest, with a tie going to the member whose significand is even. This is the default, and the only one Python's `float` ever uses.
- **RN away**, to nearest, with a tie going to the larger magnitude.

The two RN functions agree except on an exact tie, and whatever RN returns is always RD(x) or RU(x); the program checks both on 1,025 inputs. Ties go to even by default because that has no bias: across many ties, about half go up and half go down, where ties-away pushes every one of them outward. Python's `decimal` module has all five under other names, and its `ROUND_HALF_UP` is ties-away, the rule most people learned at school.

Directed rounding is not a curiosity. RD and RU are how [interval arithmetic ↗](https://masiarek.github.io/rust-learning-library/09_Advanced/interval_arithmetic/index.html) keeps a lower and an upper bound that are guaranteed.

## Which laws survive, and why those

Section 4 is a proof by exhaustion for the toy system: every pair and every triple of members was tried. In the output, (+) stands for ⊕. The pattern in the verdicts is the useful part.

| law | verdict |
|---|---|
| a ⊕ b = b ⊕ a, and a ⊗ b = b ⊗ a | holds |
| a ≤ b implies a ⊕ c ≤ b ⊕ c | holds |
| a ⊖ b = 0 implies a = b | holds — **only with subnormals** |
| b/2 ≤ a ≤ 2b implies a ⊖ b is exact | holds — **only with subnormals** |
| (a ⊕ b) ⊕ c = a ⊕ (b ⊕ c) | fails |
| a ⊗ (b ⊕ c) = (a ⊗ b) ⊕ (a ⊗ c) | fails |
| b ≠ 0 implies a ⊕ b ≠ a | fails |
| a ⊗ (1 ⊘ a) = 1 | fails |

The laws that survive compare **one exact result with itself**. `a + b` and `b + a` are the same real number before any rounding happens, so they round to the same member. And a rounding function never reverses the order of two numbers, so monotonicity survives too.

The laws that fail compare **two routes** to a result, and each route rounds at different points along the way. `(0.1 + 0.2) + 0.3` rounds the sum 0.30000000000000004 first and then rounds again. `0.1 + (0.2 + 0.3)` adds two stored values whose errors happen to cancel to exactly 0.5, and rounds only at the last step. Neither answer is a mistake: each is the correctly rounded result of the operations actually performed. The sibling Rust library follows this to its consequence for a compiler in [letting the compiler reorder a float sum ↗](https://masiarek.github.io/rust-learning-library/19_Numbers/letting_the_compiler_reorder/index.html).

The fourth row is **Sterbenz's lemma**: when a and b are within a factor of 2 of each other, a − b is itself a member, so the subtraction involves no rounding at all. Section 5 confirms it on a real float — `(0.1 + 0.2) - 0.3` returns exactly the difference of the two stored values. That is the precise form of what the next lesson, [catastrophic cancellation](../catastrophic_cancellation/README.md), says in words: the subtraction does not create the error, it only exposes the error its inputs already carried.

## Which numbers can be members at all

No amount of precision changes whether a fraction can be stored exactly. In radix β, a fraction in lowest terms has a finite expansion only when every prime factor of its denominator divides β. In radix 2 that means a power of two in the denominator, so 1/10 is out however many bits you allow. Radix 10 lets 1/10 in and still keeps 1/3 out, and radix 3 would do the reverse.

The Rust library walks through the binary expansion itself in [what a float actually stores ↗](https://masiarek.github.io/rust-learning-library/19_Numbers/what_a_float_stores/index.html). The point here is the one before it: the choice of β settles which fractions can ever be members, before a single digit is counted.

## Off the ends of the range

A range limit is where a wrong answer can stay silent. Among its list of well-known arithmetic bugs, the *Handbook* records a release of Maple (7.0, from 2001) that returned 1 for 1001!/1000!, whose true value is 1001.

On IEEE 754 floats that computation cannot return 1. Both factorials overflow to `inf` long before 1000 — 171! already does — and `inf / inf` is `nan`, a value that announces itself. Section 6 shows the other possibility: a system that stopped at the largest float instead would compute largest / largest = 1.0, a plausible number that is completely wrong. That is the design reason IEEE 754 has infinities and NaNs at all.

The fixes are all ways of never leaving the set: cancel symbolically first, use exact integers, or work with logarithms, where 1001! becomes a number near 5,919 instead of a number with 2,571 digits.

## The four numbers are the compromise

Section 7 puts four real formats side by side, and each parameter buys something and costs something:

- **Precision** buys significant digits. Binary16 stores 1/10 wrong in the fourth significant digit, binary64 in the seventeenth. It costs memory and time.
- **Exponent range** buys headroom. Binary16's largest value is 65,504, which is why 70,000 does not fit.
- **Radix 10** buys exact decimal fractions, which is why money uses it. It costs an uneven ruler — the relative gap varies tenfold across each power of 10, against twofold across each power of 2 — and, packed into 64 bits, fewer distinct values than binary64.
- **Radix 2** buys the most even ruler and the simplest hardware, and costs the decimal fractions people write every day.

Binary64 is the default not because it is correct — no finite set is — but because, for most numerical work, it is the best of these trades.
